# PostgreSQL migration checklist

Execute these steps in order. This checklist implements [4.2-refactor-plan.md](./4.2-refactor-plan.md); ignore the earlier plans. Unchecked items are implementation work, not completed changes.

Use pnpm for package commands. Commands below specify their working directory. Existing SQLite data is disposable. Do not run Drizzle `push`, overwrite the developer's `.env`, reset existing Docker volumes, provision Supabase, or add CI configuration.

## 1. Inspect the working tree and installed APIs

- [ ] Run `git status --short` from the repository root and preserve unrelated changes.
- [ ] Read `AGENTS.md`, `server/package.json`, `server/drizzle.config.ts`, `server/src/pkg/db/index.ts`, and `server/vitest.config.ts`.
- [ ] Confirm the installed Drizzle release supports `drizzle-orm/node-postgres`, the current `relations` configuration, and `drizzle-orm/node-postgres/migrator` with the generated migration directory format.
- [ ] Confirm the PostgreSQL driver initialization and shutdown APIs before replacing the client. Keep the installed Drizzle version unless an actual compatibility issue requires a change.
- [ ] Record existing server check failures if encountered, so they can be distinguished from migration regressions.

## 2. Verify the separate local PostgreSQL instances

Files: `docker/compose.yml` and `docker/compose.test.yml`. No initialization script is needed.

- [ ] Confirm both files use `postgres:17-alpine`, a `postgres` service, and a readiness health check.
- [ ] Confirm development has `name: expensif-dev` and a persistent named volume; tests have `name: expensif-test` and `tmpfs` storage.
- [ ] Confirm both bind to `127.0.0.1:5433:5432`. Run them sequentially, never together.
- [ ] Let image initialization create each database and user. The users are local instance superusers; separate instances replace the earlier custom non-superuser role design. Do not add `init.sql` or shared-instance grants.
- [ ] Use these host connection URLs consistently:

```text
Development: postgres://expensif_dev:local_dev_password@127.0.0.1:5433/expensif_dev
Tests:       postgres://expensif_test:local_test_password@127.0.0.1:5433/expensif_test
```

- [ ] From the repository root, validate both files and start development:

```sh
docker compose -f docker/compose.yml config --quiet
docker compose -f docker/compose.test.yml config --quiet
docker compose -f docker/compose.yml up -d --wait
```

- [ ] Verify the development login/database and confirm the test URL fails against this instance. A readiness check alone does not verify credentials.
- [ ] Switch to tests and verify the test login/database:

```sh
docker compose -f docker/compose.yml down
docker compose -f docker/compose.test.yml up -d --wait
```

- [ ] Restore development before applying development migrations in step 5:

```sh
docker compose -f docker/compose.test.yml down
docker compose -f docker/compose.yml up -d --wait
```

Checkpoint: each instance initializes independently, the wrong environment's connection fails, and only one instance is running. Do not use `down -v`: development data must survive switching. Image initialization settings affect only an empty data directory; inspect existing development volumes rather than resetting them.

## 3. Replace the driver and connection lifecycle

Run from `server`:

```sh
pnpm remove @libsql/client
pnpm add pg
pnpm add -D @types/pg
```

- [ ] Update `server/src/pkg/db/index.ts` to initialize `pg.Pool` and `drizzle-orm/node-postgres` with the existing relations.
- [ ] Delete `serializeTransactions` and its SQLite-specific comments.
- [ ] Keep the existing `initDb`, `Db`, `DbClient`, `Tx`, and `DbTx` entry points where practical to minimize caller changes.
- [ ] Set a bounded pool size that permits at least two simultaneous test transactions. Do not replace the queue with a single-connection application pool.
- [ ] Update `server/src/shutdown.ts` to await `pool.end()`.
- [ ] Update `server/.env.example` to use the local development database. Leave the existing `.env` untouched; use a command-scoped development URL when verifying migrations if necessary.
- [ ] Include package manifest and `pnpm-lock.yaml` changes.

## 4. Convert the six table schemas

Files under `server/src/modules`: `user/schema.ts`, `category/schema.ts`, `message/schema.ts`, `expense/schema.ts`, `linked-account/schema.ts`, and `api-key/schema.ts`.

- [ ] Replace SQLite builders with PostgreSQL builders.
- [ ] Preserve text IDs, nullability, uniqueness, indexes, foreign keys, defaults, and delete actions. Do not redesign identifiers.
- [ ] Use timezone-aware timestamp columns with `mode: "string"` for creation, update, receipt, linking, expiry, use, and revocation instants.
- [ ] Use a date column with `mode: "string"` for `expenseDate`.
- [ ] Use exact PostgreSQL `numeric` for `amount`; choose and document precision/scale and the runtime representation. Do not silently convert exact amounts to JavaScript floating-point numbers.
- [ ] Inspect the schemas generated by `drizzle-orm/zod` and adjust consumers only where necessary. Keep response contracts derived from Drizzle.
- [ ] Keep expense persistence out of scope; the expense service currently only parses expenses.

Checkpoint: all six definitions use PostgreSQL types and preserve their existing relationships and constraints.

## 5. Generate and apply the PostgreSQL baseline

- [ ] Change `server/drizzle.config.ts` to `dialect: "postgresql"`, retaining the schema entry point and intended migration output directory.
- [ ] Remove the old SQLite migration SQL and snapshots from the active migration directory. Git history is sufficient; do not retain a second active migration history.
- [ ] From `server`, generate the new baseline:

```sh
pnpm db:generate
```

- [ ] Review generated SQL and snapshots for all six tables, constraints, foreign-key delete actions, indexes, numeric types, date types, and timestamp defaults.
- [ ] From `server`, apply it to `expensif_dev`, explicitly supplying the local development URL if `.env` still points to SQLite:

```sh
DATABASE_URL='<local-development-postgresql-url>' pnpm db:migrate
DATABASE_URL='<local-development-postgresql-url>' pnpm db:migrate
```

Replace the placeholder with the URL defined in step 2; it must target `expensif_dev`. The second invocation must have no pending migrations.

- [ ] Include the generated migration SQL and snapshots in the eventual commit. Do not execute schema SQL directly or use `push`.

Checkpoint: a fresh development database migrates successfully and repeating migration changes nothing.

## 6. Convert services and raw SQL

Files: `server/src/modules/{auth,user,api-key,linked-account}/service.ts`, `server/src/pkg/db/error.ts`, and affected consumers.

- [ ] Replace SQLite `.get()` with bounded selects and explicit handling of a missing first row.
- [ ] Replace `.all()` and `.run()` with awaited PostgreSQL-compatible queries.
- [ ] Replace `rowsAffected` checks with `returning()` and returned-row checks.
- [ ] Replace key expiry generation's SQLite `datetime(...)` with PostgreSQL timestamp arithmetic using database time.
- [ ] Use `clock_timestamp()` in the atomic consumption expiry predicate so expiry is checked at execution time, including after a lock wait.
- [ ] Keep API key consumption, account linking, and user lookup inside the same transaction. Pass `tx` throughout; preserve rollback when linking or lookup fails.
- [ ] Keep the current behavior where an already-linked account leaves the attempted key unused. Do not implement the future behavior mentioned in a test comment.
- [ ] Map PostgreSQL unique (`23505`) and foreign-key (`23503`) errors, including Drizzle wrappers, to the existing domain behavior. Remove SQLite-specific detection.
- [ ] Fix `revokeApiKey()` so an absent selected key is checked before reading `revokedAt`.
- [ ] Use `ILIKE` for case-insensitive key label search.
- [ ] Audit count results, nullable values, raw SQL, and inferred result types.

## 7. Add suite-level test migrations

Files: add `server/src/test/db-config.ts` and `server/src/test/global-setup.ts`; update `server/vitest.config.ts`.

- [ ] Define one hardcoded local test URL in `db-config.ts`, using `127.0.0.1`, the fixed port, `expensif_test`, and its dedicated role from step 2.
- [ ] Import that constant from global setup and the test helper. Do not read an environment URL, fall back to `DATABASE_URL`, duplicate credentials, or import application setup just to obtain the constant.
- [ ] Validate the expected host, port, database, and role before destructive cleanup.
- [ ] In `global-setup.ts`, open a short-lived `pg.Pool` and apply the generated files through `drizzle-orm/node-postgres/migrator`. Resolve the migration directory relative to the setup file, not the caller's working directory.
- [ ] Await `pool.end()` in `finally`. Surface connection failures with instructions to stop development and start `docker/compose.test.yml`; do not disguise SQL or permission failures as connection failures.
- [ ] Register `globalSetup` in Vitest and set `fileParallelism: false`. Keep individual tests sequential.
- [ ] Do not run migrations in each file's `beforeAll` or use a module-level promise as a guard across workers. Do not manually parse migration SQL.

Checkpoint: migrations complete before test workers start; a missing test instance or a running development instance produces a clear failure without any SQLite or development-URL fallback.

## 8. Replace per-test SQLite setup and teardown

Files: `server/src/test/helper.ts`, the five auth test files, and `server/src/test/linked-account/redeem-api-key.use-case.test.ts`.

- [ ] Remove the manual SQLite migration reader, in-memory database creation, temporary database folders, and file deletion.
- [ ] Before each test, validate the fixed connection and truncate `users`, `categories`, `messages`, `expenses`, `linked_accounts`, and `api_keys` together in one explicit statement. Do not truncate the migration journal or use an open-ended cleanup operation.
- [ ] Build the existing app/services using the emptied test database. Preserve `initTest` and `initUseCaseTest` entry points if that keeps test edits small.
- [ ] If helper initialization fails after opening a client, close it before rethrowing.
- [ ] Change all teardown hooks to await PostgreSQL pool shutdown. Reset per-test context before setup and guard teardown when setup failed, so it cannot close a stale context or hide the original failure.
- [ ] Await all work launched by a test before teardown and before the next test truncates tables.
- [ ] Do not wrap each test in a transaction for rollback cleanup; real application transactions must use independent connections.
- [ ] Convert the existing expiry test's SQLite timestamp arithmetic to PostgreSQL.

Checkpoint: each test starts with empty application tables, keeps the schema intact, and leaves no live pool behind.

## 9. Verify behavior and real concurrency

- [ ] Keep existing authentication, expired/revoked key, duplicate-request, same-key concurrency, and rollback tests.
- [ ] Verify concurrent calls consuming one key yield exactly one success and the expected domain errors for all losers.
- [ ] Add a test where two transactions write separate rows and both reach a barrier before either can commit. Bound the wait, release the barrier in `finally`, and await both transactions on failure. This must fail if a queue or single-connection pool prevents overlap.
- [ ] Extend the real linked-account uniqueness violation test: verify the second key is unused, then successfully redeem it for a different platform account.
- [ ] Add a lock-wait expiry test: lock a key without consuming it, start consumption on another connection, confirm the attempt is waiting on that lock, and hold the lock until database time has passed the key's expiry. Release the lock and assert consumption rejects the expired key. Use bounded database waits and always release/await pending transactions on failure.
- [ ] Verify actual driver errors for unique and foreign-key violations are recognized.
- [ ] Cover revocation of an unknown key, case-insensitive label search, and response-schema validation against serialized timestamp values. Add API key or linked-account routes to the test app only as needed for those HTTP checks.

## 10. Run final verification

- [ ] Verify fresh initialization and migration separately for each Compose file. Use an isolated Compose project for development verification if the normal project already has data; do not delete its volume. Run projects using the fixed host port sequentially.
- [ ] With development running, insert a disposable development marker and confirm the hardcoded test URL cannot connect. Ensure a connection failure stops test setup before cleanup.
- [ ] From the repository root, switch to the disposable test instance:

```sh
docker compose -f docker/compose.yml down
docker compose -f docker/compose.test.yml up -d --wait
```

- [ ] From `server`, run:

```sh
pnpm test:run
pnpm typecheck
pnpm lint
pnpm format:check
pnpm build
```

- [ ] From the repository root, restore development:

```sh
docker compose -f docker/compose.test.yml down
docker compose -f docker/compose.yml up -d --wait
```

- [ ] Verify the development marker survived and remove only that marker. Verify restarting the test instance recreates its disposable database and global setup reapplies migrations.
- [ ] Fix migration-related failures; record unrelated existing failures separately.
- [ ] From the repository root, audit remaining SQLite references:

```sh
rg -n 'libsql|sqlite-core|serializeTransactions|rowsAffected|datetime\(' server/src server/package.json server/drizzle.config.ts
rg -n '\.(get|all|run)\(' server/src/modules
```

Inspect matches rather than deleting unrelated methods with the same names. Active database code must no longer depend on SQLite.

- [ ] Review `git diff` and `git status --short` for generated migrations, lockfile changes, unintended edits, and accidental credentials outside the agreed local-only setup.

## 11. Document local use and deployment boundaries

Update `server/README.md`:

- [ ] Replace npm examples with pnpm commands.
- [ ] Document the explicit `-f docker/compose.yml` and `-f docker/compose.test.yml` commands from the repository root, their top-level project names, startup with `--wait`, the shared port, and switching with `down` without removing development volumes. Include development URLs, migration/test commands, and `pool.end()` shutdown.
- [ ] Explain image-managed initialization on empty data directories, persistent development data, test `tmpfs` disposal on shutdown, and how to inspect retained development volumes when initialization settings change. No `init.sql` or custom role setup is required.
- [ ] State that test data is disposable, the test URL is hardcoded, the container must already be running, and only one suite process may use the database at a time.
- [ ] Document monetary precision/runtime representation and timestamp/date modes.
- [ ] Record later Supabase requirements: TLS, bounded per-instance pools, a connection mode compatible with transactions and prepared statements, and a direct or compatible session connection for a separate deployment migration step.
- [ ] Leave Supabase provisioning, production rollout, CI overrides, and per-worker database provisioning for later work.

Done when the generated baseline applies repeatably, PostgreSQL tests and relevant checks pass, independent transactions overlap, same-key consumption has one winner, rollback and lock-wait expiry behave correctly, and test cleanup cannot affect development data.
