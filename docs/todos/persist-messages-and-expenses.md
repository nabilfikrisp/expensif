# Message and expense persistence TODO

Implementation steps and common pitfalls for the [P1 persistence backlog](../backlogs/p1-persist-messages-and-expenses.md). Scope and acceptance criteria remain in that backlog.

1. [ ] **Define ingestion contracts.** Define separate controller, use-case, and service DTOs. The controller supplies platform identity, sender identity, original text, parsing input, source metadata, and an opaque idempotency key. Keep one expense record per message and define the successful `parseStatus` value. Pitfall: several items with one combined total are still one expense; do not invent per-item prices.

2. [ ] **Prepare the message migration.** Add a nullable, unique `idempotencyKey`; require it for new bot ingestion. Replace composite source uniqueness and review whether platform-specific metadata fields must become nullable. Define existing-row handling and preserve duplicate protection through the transition. Obtain explicit migration approval, generate SQL, have the maintainer commit it, then apply with the migrator. Pitfall: nullable keys permit multiple nulls; leaving historical keys null does not deduplicate retries of those messages. Do not fabricate missing identities or remove the old constraint without a transition plan.

3. [ ] **Add category setup.** Provide an explicit, repeatable seed command for the seven existing category choices. Add category-service operations so parsing uses database categories and unknown category output resolves to `other`. Pitfall: do not silently replace a missing required `other` row with a null category or an in-memory list; report missing setup as an error.

4. [ ] **Add message and expense persistence operations.** Implement transactional message lookup/insertion, retrieval of its saved expense, and expense insertion using injected database dependencies. Keep source metadata separate from idempotency policy. Pitfall: preserve amount strings end to end; converting through JavaScript `number` can lose precision. Validate positive whole-rupiah IDR values and date-only expense dates without rounding or currency conversion.

5. [ ] **Return completed requests before parsing.** Add an expense use case that resolves the linked owner, finds a message by idempotency key, verifies ownership, and returns the saved result. Pitfall: neither a matching key nor a surviving message authorizes another owner to read it after relinking. Do not attach old expenses to the new owner. Check transaction and row-lock requirements explicitly when returning a saved result.

6. [ ] **Parse outside the write transaction.** Load categories and parse using the fixed `Asia/Jakarta` date policy. Store no message on parsing or validation failure. Support `gua beli rokok, mie, es teh, totalnya 50k` as one combined-description expense for `50000`. Pitfall: do not hold database locks across an LLM call. Deterministic parser tests verify validation; actual language interpretation belongs in the existing manual parser check.

7. [ ] **Save atomically and resolve concurrent duplicates.** After parsing, open a transaction, revalidate the linked owner, recheck the idempotency key, and save the original message and expense together. On an idempotency-key uniqueness conflict, roll back before loading the winning result and verifying ownership. Pitfall: PostgreSQL rejects further queries in an aborted transaction. Do not classify unrelated unique, foreign-key, amount, or currency failures as successful retries. Revalidate ownership after parsing rather than relying solely on the earlier middleware check.

8. [ ] **Wire the bot through the use case.** Generate a namespaced key such as `telegram:expense:<chatId>:<messageId>` from trusted message metadata. Preserve the original message separately from the command text passed to parsing. Compose dependencies through `init*` factories and have the controller call the use case. Confirm saving after commit; log unexpected failures with context and return generic failure wording. Pitfall: a failed reply after commit does not mean saving failed and must not trigger a second expense or a misleading save-failure response.

9. [ ] **Cover observable flows with real PostgreSQL.** Test ordinary and combined-item expenses, category fallback, exact large amounts, sequential and concurrent retries, distinct messages with identical text, source separation across chats/platforms, failed parsing, transaction rollback, retry after failed confirmation, and unlink/relink ownership. Assert saved rows and responses. Pitfall: completed retries should skip parsing, but concurrent first deliveries may both parse; assert one persisted result without claiming exactly-once LLM calls. Keep routine tests free of paid calls.

10. [ ] **Consolidate existing schema coverage.** Follow the [test-consolidation backlog](../backlogs/p3-move-ingestion-schema-tests-to-persistence-tests.md). Move relevant amount, currency, metadata, and identity cases into persistence flows; remove standalone cases only after equivalent coverage passes. Retain focused lower-level tests, with explanatory comments, where broader flows cannot exercise database constraints. Pitfall: application-level rejection alone does not verify a PostgreSQL constraint. Preserve parser tests and do not duplicate the same behavior across layers.

11. [ ] **Verify and close the documentation gaps.** Run typecheck, lint, formatting, and the integration suite through the dedicated test-database runner. Update affected capability gaps and setup instructions; remove completed assigned backlog items and fix their links. Pitfall: target documents describe intent, not proof of implementation. Record verification results in the implementation response rather than appending test history to documentation.
