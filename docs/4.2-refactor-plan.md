# SQLite to PostgreSQL migration

## Scope and decisions

- Base the implementation on the current source code and this plan. Ignore `docs/4-refactor-plan.md` and `docs/4.1-refactor-plan.md`.
- Existing SQLite data is disposable. No export, import, or compatibility layer is needed.
- Use PostgreSQL through Docker Compose locally and Supabase in production. Supabase provisioning and production rollout are later deployment work.
- Keep response contracts derived from Drizzle's schema. Database type changes may flow through to those contracts; preserving SQLite timestamp formatting is not required.
- Remove the in-process transaction queue while preserving API key single-use enforcement and transaction rollback.
- Use pnpm. Generate and apply Drizzle migrations; never use `push`.
- Defer CI configuration and parallel test-suite execution.

## 1. Use separate local PostgreSQL instances

- Use `docker/compose.yml` for development (`name: expensif-dev`) and `docker/compose.test.yml` for tests (`name: expensif-test`). Each defines a `postgres` service using `postgres:17-alpine` and a readiness health check.
- Both bind to `127.0.0.1:5433`; run only one instance at a time. Stop development before starting tests and stop tests before restarting development. Top-level Compose names keep their resources separate without `-p`.
- Keep development data in a persistent named volume. Store test data in `tmpfs`, which is disposable when the container stops. Global setup reapplies migrations after test database recreation.
- Let the PostgreSQL image create each instance's user and database through `POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_DB`. No `init.sql` or custom role provisioning is needed. These image-created users are superusers inside their separate local instances; production permissions remain deployment work.
- Use different credentials and database names: `expensif_dev` / `local_dev_password` / `expensif_dev` for development and `expensif_test` / `local_test_password` / `expensif_test` for tests. The hardcoded test connection must fail against the development instance.
- Development URL: `postgres://expensif_dev:local_dev_password@127.0.0.1:5433/expensif_dev`. Test URL: `postgres://expensif_test:local_test_password@127.0.0.1:5433/expensif_test`.
- Image initialization settings apply only to an empty data directory. Do not delete an existing development volume to change credentials or database settings; inspect it and document any required manual adjustment.
- Update `server/.env.example` with the development PostgreSQL URL. Do not overwrite the developer's existing `.env`.

## 2. Replace the driver and schema

- Replace `@libsql/client` with `pg` (`node-postgres`) and add `@types/pg` as a development dependency. Use `pg.Pool`, `drizzle-orm/node-postgres`, and `drizzle-orm/node-postgres/migrator`. Check the installed Drizzle `1.0.0-rc.4` APIs before implementation.
- Update `server/src/pkg/db/index.ts`, retaining the existing `initDb`, `Db`, `DbClient`, `Tx`, and `DbTx` entry points where practical. Delete `serializeTransactions`.
- Use a bounded connection pool with at least two connections in tests. Do not serialize application transactions through a single connection.
- Await `pool.end()` in `server/src/shutdown.ts` and test teardown.
- Convert the six schema modules to PostgreSQL definitions. Preserve primary keys, nullability, defaults, uniqueness, indexes, foreign keys, and delete behavior. Existing text IDs can remain text; no ID redesign is needed.
- Use timezone-aware timestamps with Drizzle `mode: "string"` for instants and a date column with `mode: "string"` for `expenseDate`. This keeps generated Zod schemas compatible with HTTP JSON without a separate date conversion layer. Verify generated response schemas against actual serialized responses; preserving SQLite timestamp formatting is not required.
- Keep monetary values exact with PostgreSQL `numeric`; choose and document precision and runtime representation. Expense persistence is currently unimplemented, so do not add persistence logic as part of this migration.
- Change `server/drizzle.config.ts` to the PostgreSQL dialect and replace SQLite migration history with a fresh PostgreSQL baseline. Generate it with `pnpm db:generate`, inspect its SQL and snapshot, and include the generated files in the change.
- Apply the baseline with `pnpm db:migrate` against the fresh development database. Run migrate again to confirm it is a no-op. Do not apply schema changes directly.

## 3. Convert queries and preserve behavior

- Replace SQLite-only `.get()`, `.all()`, `.run()`, and `rowsAffected` usage in auth, user, API key, and linked-account services. Use normal awaited PostgreSQL queries, bounded selects, and `returning()` for affected-row checks.
- Replace SQLite `datetime(...)` in key generation and expiry tests with PostgreSQL timestamp arithmetic. Keep expiry checks based on database time. A key must still be valid when consumption executes, including after waiting for a row lock: use `clock_timestamp()` in the consumption expiry predicate rather than PostgreSQL `CURRENT_TIMESTAMP`, which is fixed at transaction start.
- Preserve the existing atomic conditional update used to consume API keys. Keep consumption, account linking, and user lookup in the same transaction, using the supplied `tx` throughout.
- Preserve current rollback behavior: a failed account link or user lookup leaves the key unused. Do not implement the test comment proposing future key-burning behavior.
- Verify unique and foreign-key error mapping against actual PostgreSQL driver errors, including Drizzle wrappers. Remove obsolete SQLite-specific detection.
- Fix the existing missing-key branch in `revokeApiKey()`: check whether the selected row exists before reading `revokedAt`, so an unknown key produces the intended domain error.
- Preserve case-insensitive API key label search with `ILIKE`. PostgreSQL Unicode matching can differ from SQLite's default ASCII behavior.
- Audit remaining raw SQL, count results, nullable values, and inferred types for PostgreSQL compatibility.

## 4. Replace test database setup

### Connection and safety

- Hardcode one local test URL in a small shared test configuration module, pointing to `127.0.0.1`, the fixed Compose port, `expensif_test`, and its dedicated role. Both Vitest global setup and the test helper must import this constant; do not duplicate the URL or import application setup merely to obtain it.
- Do not read a test URL from the environment and never fall back to `DATABASE_URL`. CI overrides are out of scope.
- Route test migrations, application connections, and cleanup through that constant. Validate the expected local host, database name, and role before destructive cleanup.
- If PostgreSQL is unavailable, fail with a clear instruction to start Compose. Tests do not start or stop containers.

### Lifecycle and isolation

- Apply the generated migration files once before the suite in Vitest `globalSetup` through `drizzle-orm/node-postgres/migrator`, using a short-lived pool that closes even on failure. Do not manually split or execute migration SQL. Do not use a per-file `beforeAll` or a module-level promise as a suite-wide migration guard; test workers have separate module instances.
- Set Vitest `fileParallelism: false` to run files sequentially. Keep individual tests sequential; do not add concurrent test declarations.
- Before each test, truncate all six application tables together. Leave Drizzle's migration journal intact. Use an explicit table list so cleanup cannot expand to unrelated schemas.
- Build services and the HTTP app against the emptied test database. Keep existing helper entry points where useful, but remove in-memory SQLite setup, temporary database files, and file cleanup.
- Close each test's pool asynchronously after the test, including failure paths. Update existing auth and use-case teardown hooks accordingly.
- Do not wrap tests in a transaction for rollback-based cleanup. Application transactions and concurrency checks must use real, independent pooled connections.
- Document that the test database is disposable and only one suite process may use it at a time. Per-worker databases or schemas are deferred until parallel execution is needed.

### Behavior and concurrency checks

- Keep existing authentication, single-use redemption, duplicate-request, expiry, revocation, and rollback tests.
- Run concurrent redemption calls inside a sequential test through a pool with multiple connections. Exactly one redemption of the same key must succeed; other calls must return the expected domain error.
- Add a bounded test proving two independent write transactions can both enter and perform writes before either is released to commit. Use separate rows, a synchronization barrier, and cleanup in failure paths so a queue or single-connection regression fails instead of hanging.
- Verify rollback after a real linked-account uniqueness violation, including that the key remains usable for a different account.
- Add a bounded expiry check where a transaction locks a key, another transaction attempts consumption, and the key expires before the first transaction releases the lock without consuming it. The waiting consumption must reject the key. Synchronize the transactions explicitly, use short database-side time bounds, and release locks and await pending work in failure paths.
- Add targeted checks for PostgreSQL constraint error mapping, missing-key revocation, case-insensitive label search, and response serialization where database types changed.

## 5. Verify and document

- Verify fresh initialization of development and test instances separately, apply development migrations, and run the full suite against the test instance. Use an isolated Compose project for fresh development verification if a development volume already exists; do not reset it.
- Verify the hardcoded test URL fails against the running development instance before any cleanup. Stop development, run the test instance and suite, then restart development and confirm its data is unchanged.
- Run `pnpm test:run`, `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, and `pnpm build` from `server`. Address migration-related failures and report unrelated existing failures separately.
- Confirm active server code no longer uses the SQLite driver, SQLite query methods, or transaction queue.
- Update the server README with pnpm commands and explicit `docker compose -f docker/compose.yml` / `docker compose -f docker/compose.test.yml` commands from the repository root. Document startup with `up -d --wait`, switching instances with `down`, development migrations, and tests. Explain persistence, disposable test data, the shared port, the hardcoded test connection, and the single-suite limitation. Do not use `down -v` to switch environments.
- Document later Supabase deployment requirements: TLS, a bounded per-instance pool, a connection mode compatible with the driver's prepared statements and transactions, and a direct or compatible session connection for migrations. Production migrations should run as a separate deployment step.

## Completion criteria

- A fresh local environment initializes successfully and the generated PostgreSQL migration applies cleanly and repeatably.
- Existing tests run against PostgreSQL with empty application tables before each test.
- Independent transactions overlap without an application queue; concurrent consumption of one key has exactly one winner; failed redemption rolls back.
- Development data is isolated from test cleanup by separate instances and storage, distinct credentials/database names, and the hardcoded test connection.
- Relevant server checks pass, generated migrations are included, and local setup is documented.
